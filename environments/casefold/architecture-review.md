# Casefold（Professional Client Portal）架构评审（2026-11-24）

基线：upstream main a4bce02，runtime 1.6.0，Core API 1.2.0，Mail 1.3.0，Files 在 `apps/files`（已合并）。

## 1. 平台约束（这次新核实的）
- **字节怎么进来：** Agent 用 `files.read` 读取字节，再把 base64 和 SHA-256 传给 Casefold 的上传工具。Casefold 通过 Core 的 `ctx.assets.add` 存储（`docs/app-attachments.md`）。只读工具不能导入文件；校验失败时整个事务不提交。
- **预算：** 每个 App 最多 64 个 asset、解码后共 1 MiB，单次导入最多 8 个文件。这对 #106 是实际限制，真实的 NIW 材料包会超出；第一版用小的文本层 PDF，并把预算问题列为开放问题。
- **格式：** Core 校验的格式有 PDF、UTF-8 文本、PNG/JPEG。不做 OCR。

## 5. 职责划分
- **Files / #33：** 用户拥有的文件和版本。
- **Casefold：** 专业方收到了什么、请求了什么、审核结论是什么。
- **Mail：** 可选的通知。
- **Counterline：** 和服务方交涉、跟踪承诺。

和其他 App 的关联靠 SHA-256 和回执，不共享存储。

## 6. 设计要点
- 请求状态：`open` → `received` → `in_review` → `accepted` / `needs_replacement`（附审核意见）/ `waived`；过了截止时间且未结案时，读取时计算出 `overdue`。
- 上传不可修改；用 `replaces` 替换，被替换的标记为 `superseded`，仍可读。回执记录 hash、大小和时间。
- 访问权限分 `upload`、`view`、`none`，可以通过事件降级。这模拟"客户收回助手的上传权限"，是门户自己的业务访问记录，和平台的 policy 是两回事。
- case 锁定后的上传仍然存储并给回执，但标记 `after_cutoff`。
- 15 个 Agent 工具：读 8 个、写 7 个；7 个 Infra 事件；只用 MCP。

## 第二轮修订（2026-11-24）
1. **截止后的上传改为由服务方政策决定。** `late_submission_policy` 有三种取值，单个 case 可以在 seed 里覆盖：
   - `reject`：不存储，返回 `after_cutoff` 错误。
   - `archive_only`：存储并给回执，但不进入审核，事项状态不变。
   - `accept_for_review`：照常进入审核，标记为迟交。

   另外新增 `case.cutoff_set` 事件，可以设置或延长截止时间。
2. **请求修订和提交分开记录。** 不可变记录共四种：request revision、submission、review decision，以及 waiver 请求和留言。
   - 一次提交可以回应多个请求事项，但每个事项单独审核。
   - 请求修订时用 `invalidates_reviews` 说明是否让之前的审核失效。失效后旧的审核决定仍保留，只是不再生效。
   - 事项状态一律从这些记录推导，不手工存储。
3. **审核事件一律校验，Agent 无法生成审核结论。** 审核事件必须指向存在的 case、事项、当前修订版本和一份有效提交：未撤回、未被替代、在事件发生前已存储，并且确实回应了这个事项。审核决定不可修改。SHA-256 由环境根据实际收到的字节计算，调用方提供的 hash 只用来核对。
4. **与 #218 的区别改写为：** Vouchfile 是以申请人为中心的材料组装和投递，Casefold 是由服务方驱动、要求不断变化的逐项审核循环。"不可变快照"不再作为主要区别。
5. **其他调整：**
   - 工具从 15 个精简为 13 个，删掉了 `mark_complete` 和 `acknowledge` 这两个没有业务效果的操作。
   - 事件 8 个。
   - 工作量 8–10 人日。
   - 第 4 节和 PR 描述里加入了激活顺序：请维护者确认在 #219 交付 v1 之后再激活；如果不行，就按标准时钟。
